# Phase 3：课后反馈闭环

## 数据边界

- `LessonFeedback` 是单节课程的逻辑反馈，`LessonFeedbackVersion` 保存不可变版本。
- 关键词录入、AI 整理和人工修改都会创建草稿版本；旧版本标记为 `SUPERSEDED`，不会被覆盖。
- `StudentMastery` 保存当前结构化掌握度，`MasteryEvidence` 保存每次获批反馈带来的变更证据。
- “下次课建议”保存在获批反馈内容中，不自动创建课程，避免 AI 未经教师确认改变课表。

## 审核事务

状态为 `PENDING_REVIEW` 的反馈才可批准。批准在一个数据库事务中执行：

1. 再次校验课程、计划条目和知识点归属。
2. 更新建议中的计划条目状态、实际分钟和进度说明。
3. 创建或匹配同学科知识点，并更新学生掌握度。
4. 为每项掌握度变更写入来源版本、前后等级和依据。
5. 固定批准版本并写入审计日志。

任何一步失败都会回滚，AI 失败也不会修改正式计划或掌握度。Phase 3 暂不允许修改已批准反馈，以避免重复应用变更；后续如需更正，将使用差异冲销而不是覆盖历史。

## AI Provider

- `mock`：开发和自动测试默认值，无费用。
- `openai`：Responses API 适配器。
- `deepseek`：OpenAI 兼容 Chat Completions 适配器，结构化任务启用 JSON object 模式并在服务端验证统一 Pydantic 契约。

业务服务只依赖 `AIProvider`，不直接导入厂商 SDK。提供商、模型名和密钥均由服务端环境变量决定。发送模型前使用由学生 UUID 派生的稳定代号和相关计划/掌握度片段，不发送学生显示名称、账户密码、API 密钥或无关材料。

## 工作流定位

当前正式事实源仍是 PostgreSQL。未来可增加 Obsidian Markdown 导出，把学生档案、错题和进度同步成便于离线浏览的 Vault；该能力必须是单向导出或具备明确冲突策略，不能让两个系统同时静默覆盖正式数据。
